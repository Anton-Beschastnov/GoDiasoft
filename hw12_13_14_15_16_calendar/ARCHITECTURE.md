# Архитектура: Календарь с Напоминаниями

В этом документе описывается архитектура системы и взаимодействие её компонентов.

## Обзор

Система построена на принципах микросервисной архитектуры. Она использует **Apache Kafka** в качестве брокера сообщений для обеспечения асинхронного взаимодействия и **PostgreSQL** в качестве основного хранилища данных.

## Компоненты системы

Система состоит из трех независимых микросервисов:

### 1. Calendar API (`calendar`)
- **Роль:** "Фронт-офис". Единственная точка входа для клиентов.
- **Обязанности:**
    - Предоставление REST API (создание, получение, обновление, удаление событий).
    - Валидация входящих данных.
    - Синхронное взаимодействие с таблицей `events` в PostgreSQL.
    - Обслуживание Swagger UI.
- **Особенность:** Этот сервис ничего не знает о механизме напоминаний. Его задача — просто сохранить событие.

### 2. Планировщик (`scheduler`)
- **Роль:** Фоновый рабочий процесс / Продюсер (Producer).
- **Обязанности:**
    - Периодическое сканирование таблицы `events` в PostgreSQL (по умолчанию — раз в минуту).
    - Выборка событий, для которых наступило время отправки уведомления (`start_time - notify_before <= time.Now()`).
    - Формирование сообщения (уведомления) и его отправка в топик Kafka (`calendar_notifications`).
    - Очистка базы данных от очень старых событий (старше 1 года).

### 3. Хранитель (`storer`)
- **Роль:** Фоновый рабочий процесс / Консьюмер (Consumer).
- **Обязанности:**
    - Непрерывное чтение сообщений из топика Kafka (`calendar_notifications`).
    - Сохранение полученных уведомлений в отдельную таблицу `notifications` в PostgreSQL.
    - В реальном мире этот сервис мог бы отвечать за непосредственную отправку email или push-уведомлений.

## Схема взаимодействия (Поток данных)

Процесс от создания события до фиксации напоминания выглядит следующим образом:

1. **Создание:** Клиент отправляет HTTP POST запрос к **Calendar API** с данными события (включая `notify_before`).
2. **Сохранение:** **Calendar API** сохраняет эти данные в таблицу `events` (PostgreSQL) и возвращает клиенту ответ `201 Created`.
3. **Сканирование:** **Scheduler** регулярно опрашивает PostgreSQL. Как только условие времени выполняется, он извлекает данные события.
4. **Отправка:** **Scheduler** отправляет сообщение с деталями события в топик Kafka.
5. **Получение:** **Storer** читает это сообщение из Kafka.
6. **Фиксация:** **Storer** сохраняет информацию об отправленном уведомлении в таблицу `notifications` (PostgreSQL).

## База данных

Используется PostgreSQL с двумя основными таблицами:
- `events`: Хранит информацию о событиях (создается/изменяется через API, читается Scheduler'ом).
- `notifications`: Хранит архив отправленных уведомлений (пишется Storer'ом).

## Почему именно такая архитектура?

- **Отказоустойчивость:** Если `storer` упадет, `scheduler` продолжит генерировать уведомления в Kafka. Когда `storer` поднимется, он обработает накопившиеся сообщения без потери данных.
- **Масштабируемость:** Мы можем запустить несколько экземпляров `storer`, чтобы быстрее обрабатывать большую очередь уведомлений (через механизм Consumer Groups в Kafka).
- **Слабая связанность:** `calendar` и `scheduler` ничего не знают о том, как именно отправляются/сохраняются уведомления. Логику `storer` можно полностью переписать без ущерба для остальных компонентов.
